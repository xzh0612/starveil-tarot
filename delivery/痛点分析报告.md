## 3. 痛点详述

### 3.1 P0-1 合规敞口：AI 算命监管 + 显式标识缺失

- **现象**：项目有免责边界雏形（塔罗解读用于自我反思、不读取他人内心、不保证未来事件；健康/法律/投资问题要求现实依据边界——D1 §设计边界、D2 §11），但**没有显式「AI 生成内容」标识的实现记录**，也未按监管要求做落点设计。
- **证据**：SR-13《人工智能生成合成内容标识办法》（四部门，2025-09-01 施行）要求显式+隐式标识；SR-14 中央网信办 2026-04「清朗·整治 AI 应用乱象」专项行动明确把「AI 算命」列入整治对象；SR-15 为施行报道。项目侧 D2 §11 仅有高危动作边界，D1 §设计边界有定位声明，均无标识落点。
- **影响**：一旦公开部署、收费或宣传预测准确性，存在被认定违规的风险（下架/封号/法律责任）；G2 调研将其列为最高风险 R-01（严重程度：高）。
- **业界参照**：四家标杆均无公开合规模块可采购（B1/B2 闭源、B3/B4 个人开源项目）；合规只能自建。
- **建议方向**：按最严口径自纠——解读面板与导出档案加显式 AI 生成标识；站稳「自我反思工具」定位；不做准确率承诺、不收费预测；收费前咨询法律专业人士（SR-14 对「反思定位」产品的执法边界未明示，G2 列为待确认 U-02）。

### 3.2 P1-1 解读质量保障缺数据闭环：门禁阈值靠真机调试试出来

- **现象**：证据门禁（`parse_reading_output` → `_claim_supported_by_evidence`）在真实 DeepSeek 调用下被逐层误拒，经**三轮真机调试**才达到职业/关系两类真实请求均返回 200；修复路线从「动词词表白名单」改为「结构化判定（可安排+可观察）」与「比例门槛」。
- **证据**：D9 §已知未解决、D10 全节（5+ 个 fixture 覆盖不到的门禁 bug：invalid_synthesis / card_reading_support / goal_section_evidence / action_reason_support / unsupported_reference_claim / goal_section_support / action_concreteness / action_text_support / synthesis_support；试错记录：行动门槛先降 0.5 导致既有契约测试被误放行，退回 2/3）。当前门槛为经验值：`_GOAL_SECTION_SUPPORT_RATIO=0.5`、`_SYNTHESIS_SUPPORT_RATIO=0.5`、`_ACTION_TEXT_SUPPORT_RATIO=2/3`、`STARVEIL_SUPPORT_RATIO=0.75`。
- **影响**：门禁阈值没有标注集验证，换模型、改 prompt 或进入新问题主题时可能再次误拒（G2 风险 R-02，严重程度：高）；「词表追不完」的教训已记录，但比例门槛的具体数值仍是调试分布（如实测 0.44–0.74）中拍的经验值。
- **业界参照**：G2 调研确认**四家标杆均无公开的证据校验层**——B3 同为个人开源项目亦无测试/评测/校验。STARVEIL 的自建门禁处于自行前沿，既是差异化优势，也是无业界背书的脆弱点；可借鉴的只有「结构化输出约束 + 一次有界修复」模式（SR-05 与 D2 §9 相互印证）。
- **建议方向**：建 50–100 条人工标注真实问题集（G2 §4.3，SR-09 口径），在同一 holdout 集上测 Recall@k、目标层级覆盖率、无关证据率、门禁通过率，把经验阈值变成可回归的数据；三轮调试样本固化为参数化回归用例（D10 已新增 9 条，需继续扩大）。

### 3.3 P1-2 测试覆盖缺口：CI 不覆盖 Python agent 测试

- **现象**：GitHub Actions 只执行前端 Node 测试与 `server-js-reference/` 的离线评估；**Python agent 的 337 个 pytest 用例只能在本地跑**（沙箱还需 `--basetemp` 规避 temp 目录限制）。
- **证据**：D1 §测试（CI 明确「不覆盖 Python agent 的 312 个 pytest」——数字为文档时点，最新为 337，见 §4 冲突裁决 C-3）；D9 §关键常量（basetemp 要求）；D10（337 passed）。
- **影响**：门禁与 Prompt 的核心逻辑（解读服务的全部校验链）没有 CI 保护，回归依赖开发者本地自觉；fixture 与真实模型输出之间存在行为差（P1-1 的 5+ 个 bug 即由此暴露）。
- **业界参照**：B3/B4 均无自动化测试；B1/B2 闭源不可见。业界个人项目普遍无测试，但这是「同样差」而非「可以接受」——STARVEIL 已有 337 个用例，缺的只是 CI 接入。
- **建议方向**：CI 增加 Python agent pytest 作业（无需 DeepSeek 密钥，用假 transport 注入）；把「真实调用样本→fixture」的转化固化为流程（D10 已用 `STARVEIL_DUMP_RAW` 转储，可直接沉淀）。

### 3.4 P1-3 数据仅存浏览器：无导入、跨设备同步与备份

- **现象**：本地档案、后记、个人知识库全部存在当前浏览器（localStorage 域），刷新可继续原牌局，但**不支持导入、跨设备同步或自动备份**。
- **证据**：D7 §明确边界「所有记录存在当前浏览器；尚不支持导入、跨设备同步或自动备份」；D2 §15 同向。
- **影响**：换设备、清理缓存或浏览器故障会导致用户历史资产丢失（G2 风险 R-05，严重程度：中）；对「全屏单页沉浸体验 + 档案回看」的产品定位，资产可持续性是信任基础。
- **业界参照**：B3 同样 localStorage 仅 12 条、无跨设备方案；B1/B2 为云端账号体系（以隐私收集为代价）；B4 纯本地无账号。业界没有「本地优先 + 云同步」的轻量默认答案。
- **建议方向**：先补 JSON 导出/导入闭环（导出已有，导入缺失）作为兜底；多用户/云同步与 P1-5 合并决策，引入前明确迁移路径，不静默改变存储位置。

### 3.5 P1-4 表现层「方案已设计、未实施」+ 3D 性能无度量验收

- **现象**：UI 重设计报告（D3）已给出完整的「可拆分舞台七层方案 + 四档设备预算 + 四阶段实施顺序」，但当前实现仍是**海报式场景拼装**：房间/桌子/人物不是真实空间对象，牌带是 CSS 绝对定位图片（无厚度/遮挡/桌面接触/光照），面板打开像覆盖在背景上的窗口，进入/抽牌/翻牌/解读/档案之间缺连续镜头编排（D3 §1 五条）。
- **证据**：D3 §1（五条表现层痛点）、§9（四阶段实施顺序）；D8 §仍未达到最终标准（P1 骨骼/布料未完成、P2 复杂牌阵几何布局、P2 档案非 3D 图书馆、主包含 Three.js 体积提示）；D7 §当前可操作能力（2.5D 动态立绘 v3 为默认，3D 模型为实验文件）。
- **影响**：设计债务持续累积——方案文档（D3 约 27K 字符）与实现之间的 gap 本身成为维护负担；「全屏单页沉浸体验」的核心承诺缺少可验收的性能证据。
- **业界参照**：SR-07/SR-08 给出可操作基线（draw call 移动端约 100–150 上限、`setPixelRatio(min(dpr,2))`、静态场景按需渲染、显式 dispose、reduced-motion 降级、真机度量），与 D3 §7 四档预算可互相校准；B3（Three.js 仪式舞台）证明同栈可行，B4（3D 扇形+手势）证明扇形牌带交互有同类实现。
- **建议方向**：按 D3 §9 阶段 A→D 推进，每阶段以「可观察交互」为验收标准（D3 §8 八条）；先补性能度量（draw call/帧率/主包体积真机数据）再扩量；主包拆分（见 P3-1）。

### 3.6 P1-5 多用户/公开部署演进路径未决策

- **现象**：当前为单用户本地优先产品；资料明确「如果未来多人使用，应该增加登录、用户隔离、后端数据库、配额和审计日志」，并指出**纯静态站点（GitHub Pages 类）不能安全代理付费 API**；该决策一直挂在「待决策」状态。
- **证据**：D2 §15（部署限制 + 多用户需求清单 + 稳妥推进顺序）；D7 §明确边界（无登录/云端数据库）；D1 §架构（worker 部署层为静态资源 + SPA 回退）。
- **影响**：演进路径不清导致两个下游问题无法回答——公开部署时密钥与配额的存放方式（现仅 loopback 本机方案），以及合规重评时机（与 P0-1 联动）。
- **业界参照**：SR-16 给出低成本候选：PocketBase（单 Go 二进制 + 内嵌 SQLite + 内置 auth，MIT，适合单节点小规模，SQLite 单写是上限）与 Supabase（Postgres 多容器，功能深但运维重）；两者都会改变「本地优先、数据不出本机」形态，需先过合规重评。DeepSeek 公开定价约 $0.14/$0.28 每百万 token（SR-17），2026-08 起峰谷计价高峰两倍（SR-18）——个人项目应错峰 + 模型快切（已具备）。
- **建议方向**：维持「先确认是真实需求再演进」的纪律（G2 §4.1 建议暂缓）；把「公开部署的最小安全形态」（服务端代理 + 配额 + 显式标识）作为与 P0-1 合并的合规包一起设计。

### 3.7 P2-1 文档同步债：多处口径不一

- **现象**：项目资料之间存在 5 处口径冲突（G1 §3 并列保留 X1–X8，其中影响文档可信度的是 X1/X2/X3/X6/X7；X4/X5/X8 已有明显示意，见 §4）。
- **证据**：X1 后端 pytest 312（D1/D2）vs 337（D9/D10 最新）；X2 前端 294/299（D2 内部）/277（D7）/29（D11）/34（D1/D9/D10/D11 末节）；X3 女巫方向（D5 3D Nyx v2 vs D6 明文 v3 立绘 supersedes）；X6 选牌布局（D6/D7 6×13 网格 vs D6 Latest card selection 明文弧形牌带 supersedes）；X7 AI 成熟度（D8 第一版验收快照「接口阶段」vs D1/D7/D11 迭代后「多轮解读/模型快切/语音已实现」）。
- **影响**：新人（或未来的自己）读文档会得到矛盾事实；README 的测试数量与 CI 描述已过期；frontend/README（D7）未同步弧形牌带与 v3 立绘。
- **建议方向**：按 §4 裁决结果一次性同步 README、frontend/README、design-qa 的状态标注（design-qa 的「final result: blocked」应改注为「第一版验收快照，后续已迭代」）。

### 3.8 P2-2 双实现并存：Node 参考实现与 Python agent 同步维护

- **现象**：解读 agent 已从 Node ESM 中间件迁移为独立 Python 服务，原实现保留在 `server-js-reference/` 作为离线评估与逐条行为对照的参考。
- **证据**：D1 §架构（迁移说明 + 参考定位）；D7 §测试（`npm run test:reference` 277 个保留）；D2 §16（Node 294 项通过的旧口径）。
- **影响**：两套逻辑并存意味着规则改动（路由/检索/门禁）需要判断是否同步参考实现，否则离线评估的「对照基线」会漂移；D10 记录过「检索是纯词汇 BM25（reading_rag.py），无 embedding」与 Node 侧表述的细微差别（X4）。
- **建议方向**：明确参考实现的冻结策略（只修 bug 不追新特性），或在 README 明示「参考实现定格于迁移时点，评估以 Python 侧为准」。

### 3.9 P2-3 agent 生命周期摩擦

- **现象一**：改了 agent 代码必须重启 8787 才生效——常驻 agent（旧 PID）会继续跑旧代码，页面上看不到变化。
- **证据**：D9 §常见故障「改了 agent 代码必须重启 8787 才生效」；D10（8787 常驻实例 PID 23266 旧代码，验证用 8788 临时实例；第三轮 kill 旧实例重启后 8787 恢复）。
- **现象二**：只起 Vite 不起 agent 时，`/api` 代理返回 500，前端显示「解读服务暂时未连接。牌面已保留」。
- **证据**：D1 §本地运行（提示语与修复方法）；D9 §常见故障。
- **影响**：开发调试期反复踩（D9/D10 均有记录）；前端提示语已把故障原因说清，并有对话面板引导卡可配密钥，属「有缓解」而非「已根治」。
- **建议方向**：`dev:all` 已做互相守护；可在 agent 加文件监听自动重启（uvicorn --reload 等价物）或在首页状态卡显示 agent PID/版本号，让「旧代码还在跑」可观测。

### 3.10 P2-4 环境坑反复踩

- **现象一**：本机 HTTP_PROXY 下 `git push` 报 `curl 16 HTTP2 framing` / `Empty reply`；绕代理直连被墙。可行解：保留代理 + `git -c http.version=HTTP/1.1 push origin <sha>:refs/heads/codex/RAG`，必要时按 commit 分批推。
- **证据**：D9 §踩坑、D10 §验证与提交（e2e7f12 尚未 push 即与此有关）。
- **现象二**：沙箱 pytest 默认 temp 目录被 broker 拒绝（22 errors），必须带 `--basetemp=/tmp/...`。
- **证据**：D9 §关键常量、D10（312→337 各轮均带 basetemp）。
- **影响**：每次推送/跑测试都要回忆参数；已有可行解但未沉淀为脚本或文档固定条目。
- **建议方向**：把两条命令写进 README 的「常见问题」或 `scripts/` 帮助命令；push 分批流程可脚本化。

### 3.11 P2-5 遗留未完成项：精细 3D 女巫与复杂牌阵几何布局

### 3.12 P3-1 主包含 Three.js 有体积提示

## 5. 当前状态的正面确认（对照：这些问题不是痛点）

为避免「为列痛点而列痛点」，以下经调研确认的现状**不属于痛点**，是项目的既有优势：

1. **服务端密钥路线正确**：密钥只存后端 `.env.local`、禁止 `VITE_` 前缀、loopback+Origin+Host 三重校验、密钥不回显——B3 标杆的 `VITE_DEEPSEEK_API_KEY` 反面实践恰好印证这条约束的价值（D1 §DeepSeek 配置、D9 §密钥配置；G2 §2.2.3）。

3. **结构化输出 + 一次有界修复是业界共识结构**：STARVEIL 的证据门禁虽缺数据闭环（P1-1），但「JSON 契约 + 引用校验 + 有界修复」的方向本身被 B3 等同栈实践印证（SR-05）。
4. **对话体验已完成产品化迭代**：全屏三栏、历史存档、模型快切、语音输入、左右栏收起均实现且有测试与实测截图（D11、D10）。
5. **高危边界覆盖完整**：健康/法律/投资动作边界、他人内心不可验证、绝对预测拦截、混合目标分段——这些是四家标杆都没有的自行前沿设计（D2 §9~§12）。
