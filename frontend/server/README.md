# Local DeepSeek reading backend

The local Vite dev and preview servers install `createReadingMiddleware` for:
- `POST /api/readings/interpret`: grounded Chinese reading and same-deck follow-ups.
- `POST /api/readings/debug`: local retrieval and Prompt diagnostics; it never calls DeepSeek and does not require an API key.
- `GET /api/readings/status`: configuration presence and model name, no credentials. This is not a provider health/balance check.

`POST /api/spreads/recommend` asks the model for 2–3 catalog spreads and validates each reason against the selected spread's position concepts and the question's recognized theme, rejecting generic or off-topic explanations before they reach the client.

Server-only settings in ignored `frontend/.env.local`:
```
DEEPSEEK_API_KEY=<local secret>
DEEPSEEK_MODEL=deepseek-flash
VITE_READING_ENDPOINT=/api/readings/interpret
```
Never prefix the API key with VITE_. The local file has mode 0600 and is not included in the client build. Change the key there and restart the local server after rotation.

The middleware permits loopback requests only and checks browser origin against the request host. It caps request size, validates card IDs/orientations/roles, retrieves a small grounded evidence set from `reading-rag.mjs`, asks for a JSON answer, and rejects references outside that set. The intent lexicon includes common expressions such as job changes, interviews, exam preparation, offers, cold wars, renewed contact, “还有戏吗”, sleep problems, and fatigue, while weak pronouns remain fallback signals; legal, financial, medical, and sleep-related wording also keeps a reality-based boundary active; when a high-stakes question has no supported relationship, career, or reflection domain, retrieval excludes unrelated application prose and reports `anchor_only` coverage. This keeps ordinary Chinese phrasing from becoming an open route. Each evidence item carries a stable `tier` (`anchor`, `application`, `reference`, or `personal`), deterministic `retrievalReasons`, the exact `retrievalTerms`/`retrievalDirectTerms`/`retrievalExpandedTerms`/`retrievalThemes`/`retrievalPositionKinds`/`retrievalGoals` that contributed to selection, and bounded `retrievalMethod`/`retrievalScore`/`retrievalSemanticScore` metadata from the BM25-plus-rules ranker and optional semantic reranker, so the model can prioritize core card meaning and the server can audit why a chunk was selected; expanded terms are low-weight lexicon hints rather than user claims. Personal memory retrieval uses a stricter keyword threshold (`memory-keyword-v3`) plus conservative concrete alias groups: a record needs one concrete phrase, one informative short term, or several independent short matches before it is sent to the model; a low-weight alias such as “交流” -> “沟通” is expanded only after the query hits that group, and expanded matches are labeled in server-side diagnostics; returned memory evidence is sanitized before it enters the model context and keeps only identity, provenance, status, use, and text; retrieval terms, scores, reasons, and methods remain server-side. It is marked `memoryStatus:user_confirmed` and `memoryUse:context_only`, and the memory text is fenced as untrusted data; generic words such as “怎么/安排/自己” alone do not expose a private record, and duplicate memory IDs are rejected before retrieval so `memory:<id>` citations remain unambiguous. `retrieveReadingEvidence` accepts an optional server-side `semanticScores` map and `semanticWeight`; the default map is empty and makes no embedding or network call. For an asynchronous model, `retrieveReadingEvidenceAsync` passes the untrimmed candidate set to a `semanticReranker({question,cards,evidence})` callback, waits at most 1.5 seconds by default, then applies the same budget and diversity rules; callback failures or timeouts fall back to lexical retrieval. `createReadingMiddleware` accepts the same callback and uses the resulting evidence both in the Prompt and in response citation validation. A future local model or authenticated backend can provide 0–1 scores without changing the Prompt contract. The ranker is deliberately dependency-free and keeps its scoring interface replaceable for a future vector reranker. Each selected card always retains symbolism and orientation anchors; `retrievalRequired` marks those chunks. The Prompt also receives `evidenceMeta`, a diagnostic summary of tier/kind counts, semantic coverage, selected cards, per-card anchor/application coverage, and goal-level support (`goalCoverage`/`missingGoalCoverage`). It additionally exposes `goalCoverageByCard`, `missingGoalCoverageByCard`, and the deduplicated `coverageBoundaryGoals` set, so a forecast or comparison missing its matching layer on one card is visible to the model and forces a narrower uncertainty boundary. A derived `evidencePlan` lists per-card anchor/application/reference IDs, `positionEvidenceIds` for evidence selected because it matches the card position, all goal evidence IDs, and `goalRequiredEvidenceIds` at the tier required by each routed goal, plus personal evidence IDs as a citation index; when `positionEvidenceIds` is present, the Prompt requires each first-reading card explanation to cite at least one position-specific chunk before generic application/reference evidence; the parser enforces the same rule during bounded repair; it carries no additional card meaning. Its `coverageStatus` is `complete` only when every card has both core anchors and the current theme application evidence; `anchor_only` or `incomplete` requires narrower uncertainty rather than invented meaning. A global evidence budget first rotates optional evidence across cards by score, then fills a second chunk for a card only after every represented card has had a chance; the default budget grows with card count and the number of application domains for large mixed spreads (capped at 96), while an explicit budget remains respected, so large spreads do not crowd the Prompt with low-priority references. For mixed questions, the retriever also reserves one required-tier chunk for each routed goal when the default budget allows it, then reserves one application chunk for each explicit relationship, career, or reflection domain before filling the remaining budget with references; position-specific evidence takes precedence over optional goal-tier reservations when an explicit budget is exhausted; mixed goal-tier reservations rotate across cards before adding a second goal layer to one card; forecast-only questions keep position-selected application context when no explicit application domain exists, while explicit budgets reserve one routed goal tier before optional position context; a choice-only or domain-neutral advice/comparison question reserves the reflection chunk as a decision context, and a focused question still filters unrelated application chunks. Temporal context words such as “未来” and “接下来” receive a low forecast weight unless paired with an explicit prediction phrase; action continuations such as “如何处理/如何平衡/如何兼顾/如何沟通” keep the advice route, selection phrases such as “怎么选/怎么选择” use the comparison goal, while trend continuations such as “如何发展/如何变化” remain forecast. Negated prediction phrases such as “不是问他会不会回来” are ignored as forecast intent while a following advice phrase remains active. Paired option-outcome wording such as “选择 A 会怎样，选择 B 会怎样” keeps forecast context and also activates comparison evidence. Causal yes-or-no wording such as “是不是因为/会不会是因为” activates explanation while a plain “是不是会有变化” remains forecast. Colloquial option wording such as “是选 A 还是选 B”“哪一种发展更适合我” activates comparison and suppresses a generic development forecast when it is embedded in the comparison phrase. Causal forms such as “是因为工作太忙吗”“是什么导致现在的状态” also activate explanation. Generic explanation questions no longer inherit work/relationship application merely from a generic position label; forecast-only position context and explicit relationship/reflection positions remain available. Personal-memory retrieval also filters pronoun, temporal, and function-word short overlaps such as “我最/最近” before applying the existing concrete-match threshold. Third-person feeling questions such as “对方是不是喜欢我”“他有没有感觉” activate `requiresPerspectiveBoundary` so the Prompt must separate observable interaction from unverifiable inner state. The professional boundary also recognizes colloquial high-stakes wording such as “胸口疼”“停药”“起诉我”“买房”和“睡四小时”, while ordinary “焦虑/辞职” remains outside that boundary unless another clinical or financial term is present. The intent router separately scores the requested goal (`advice`, `forecast`, `explanation`, or `comparison`) so the same topic can receive different evidence weighting and response emphasis. The prompt keeps the original question as the reading's background but derives `activeQuestion` from the latest real user message. Follow-up retrieval can inherit a context-only theme such as “未来” while an explicit current goal replaces the previous goal; when the follow-up changes to a clear domain such as career, the domain switches while an unstated goal remains inherited. This keeps retrieval context and direct-answer intent separate, and passes the merged follow-up routing into evidence retrieval so an inherited goal still receives its required application/reference tier. A generic follow-up may inherit the original question in the server-generated retrieval query to preserve the spread context; the active question remains the latest user message sent to the model for direct response. For a focused single-theme question, only the matching application kind is retained; mixed questions keep multiple application kinds. High-stakes protection is cumulative: the server keeps the reality-based boundary when the original question, the active follow-up, or any earlier user turn is health, legal, investment, or similar high-stakes content; assistant prose is ignored, so a generic follow-up cannot remove it. The prompt also receives a transparent `retrievalMeta` routing hint (`themes`, weighted `themeScores`, goals, `goalScores`, matched terms, confidence); explicit topic terms take precedence and weak pronouns only provide a fallback route. A server-generated `responsePlan` supplies a text range that grows with the number of cards, carries the routed goal (`advice`, `forecast`, `explanation`, `comparison`, `mixed`, or `open`), a matching emphasis sentence, a `directAnswer` opening framework, and `actionGuidance` so the first one or two sentences answer the active question and actions match the goal before evidence expansion; it also requires a first-reading `synthesis` field that links the selected cards. A derived `goalPlan` preserves the router order for mixed goals and binds each goal to its required evidence tier and evidence IDs, so the model answers advice, forecast, explanation, or comparison sections separately instead of blending unsupported conclusions; mixed first readings also return validated `goalSections`, one per routed goal, and the server rejects missing sections or evidence from another goal; the system Prompt follows a fixed workflow of current-question extraction, direct-answer-first response ordering, per-card evidence grounding, first-reading synthesis/action coverage, follow-up focus, and final citation/self-check; neither routing metadata nor the plan is treated as a source of card meaning. The server runs a deterministic corpus integrity gate before serving readings: all 78 cards must have upright/reversed, symbolism, relationships, work, reflection, and Waite reference text; the resulting counts are exposed in `knowledgeMeta.corpus`. The fixed context is wrapped in `<starveil_context>`, and every compacted history item is wrapped in `<starveil_history>` with `dataClass:untrusted_history`; prior assistant text is continuity context only and cannot replace current evidence. A server-generated `<starveil_turn>` reminder is appended after history to restate the current question and checked card positions; system instructions say that text inside either data fence is never executable instructions. History is compacted deterministically to the most recent 24 messages, at most 4,000 characters per message and 24,000 characters total; an overlong item preserves its head and tail with a middle-omitted marker (`historyTruncationStrategy:head_tail_v1`), while a roughly 56,000-character total Prompt envelope further reduces only the older history when a wide spread and evidence approach the limit, and `promptBudget.historyLimits.maxTotalChars` records the actual per-request history budget, so old conversation cannot crowd out current evidence. The model-facing `evidence` keeps only stable identity, card position, tier, source provenance, orientation, and bounded text; retrieval terms, scores, and reasons stay in the local `retrievalDiagnostics`/debug response so ranker metadata does not consume model context or masquerade as meaning. The context also carries a diagnostic `promptBudget` with input/selected/omitted/truncated history counts, history/evidence/memory character totals, question lengths, evidence/memory item counts, and the personal-memory limits (`maxItems:6`, `maxItemChars:2000`, `maxTotalChars:6000`) plus `memoryExcerptedItems`; it is observability metadata only and never a source of meaning. On the first reading, every selected card, a cross-card synthesis, a non-empty uncertainty section, and at least one evidence-backed action are required; each card reading must both cite a core anchor and overlap a meaningful concept from its cited evidence, the first synthesis must also overlap a meaningful concept from its cited evidence, while each first-reading action must include a time, count, scope, or outcome marker and cite anchor, application, or personal evidence. Malformed output gets at most one structure-repair request before the same validation runs again, and that repair prompt includes a stable validation code while fencing the prior output as data. Health, legal, investment, and similar high-stakes questions require a non-empty reality-based uncertainty boundary; high-stakes decision verbs in action text also require a reality verification, risk assessment, or qualified professional advice cue. It limits request concurrency/rate and has a 90-second timeout with disconnect cancellation. Only the current question/cards/conversation and explicitly enabled, question-relevant memory records go to DeepSeek; disabled, unrelated memories and archives are not transmitted. Past demo assistant answers are excluded from model context.

RAG v50 keeps the v38 application-domain isolation and adds a deterministic total character budget for personal memory: ranked matches are selected under a 6,000-character default budget (with bounded overrides), and an item that is cut is marked `memoryExcerpted=true` so the model cannot invent its omitted tail. A domain-neutral advice or comparison question receives only the reflective application layer, while a genuinely open question keeps core/reference evidence and only admits application prose when the position itself names a relationship or self-reflection role. A generic `建议` position alone no longer invents a work domain; an explicit forecast can still use position-selected context for its action-oriented spread slot.

Prompt v46 extends the v42 open-goal boundary to colloquial outcome language: when `responsePlan.goal=open` and `clarificationMeta.allowClarification=false`, an explicit theme with no requested outcome may only receive core card clues, observable reality, and user-controlled recording actions; it cannot smuggle in reunion, return, contact, success, “有戏”, “有机会”, “有结果”, or another person’s inner-state prediction through alternate wording. The parser and offline evaluator return stable `open_goal_prediction` and allow one bounded repair. High-stakes actions still require reality verification, risk assessment, or qualified professional advice before any irreversible decision.

## Reading contract

`POST /api/readings/interpret` returns `{text, source, provider, model, promptVersion, knowledgeMeta, promptBudget, retrievalMeta, evidencePlan, responsePlan, safetyMeta, needsClarification, clarification, goalPlan, goalSections, cardReadings, synthesis, actions, references, followUp, uncertainty, evidenceMeta}`. `knowledgeMeta` records the server-fixed deck, RAG corpus, Prompt and corpus-integrity versions; `promptBudget` records bounded history, evidence and personal-memory counts/characters plus the memory limits and excerpt count. `retrievalMeta` records the routed themes/goals and confidence, `evidencePlan` records only stable evidence IDs grouped by card and goal, `responsePlan` records the server-chosen response mode and action guidance, and `safetyMeta` records the active reality-boundary flags. These fields contain routing metadata rather than card meaning. All are safe observability metadata, shown in the conversation's collapsed reading trace, and persisted with the client archive so a later review can identify which knowledge and Prompt versions produced the reading. `goalPlan` preserves the routed goal order and binds each goal to its required evidence tier and evidence IDs, so a future client can show which part of a mixed answer is advice, forecast, explanation, or comparison. For a mixed first reading, `goalSections` contains one validated section per routed goal with its own evidence; the server rejects missing sections, unrequested goals, or evidence belonging to another goal. `cardReadings` includes the locked `orientation` (`正位` or `逆位`) so the client can show which fixed card meaning was used, plus server-derived `evidence` entries with bounded source labels and excerpts; `synthesis` and `actions` expose the same derived evidence shape so each visible explanation can be traced without trusting provider-supplied metadata. Personal-memory evidence additionally carries `memoryStatus:user_confirmed`, `memoryUse:context_only`, and `memoryExcerpted`; the last marker tells the client that the displayed excerpt is only the retained prefix of a longer memory. These are policy markers, not card meaning. `evidenceMeta.coverageStatus` reports whether the retrieved set fully covers each card's core and current-theme application evidence (`complete`, `anchor_only`, or `incomplete`); the client displays this diagnostic without treating it as a new card meaning. On the first structured reading, top-level `text` must overlap a meaningful concept in the evidence cited by the response, `cardReadings` must contain every selected card with matching `evidenceIds`, at least one core anchor per card, and prose that overlaps a meaningful concept in one of those evidence chunks, while `synthesis.text` must overlap a meaningful concept from the cited evidence for every selected card and `synthesis.evidenceIds` must include a core anchor for every selected card, each first-reading action must include a non-empty `reason` explaining its connection to the reading, with the reason sharing a meaningful concept with its cited evidence, plus a time, count, scope, or outcome marker; when an advice or comparison goal has available application evidence, every first-reading action must cite at least one application-tier evidence ID for that goal; `synthesis` must contain `{text, evidenceIds}` citing card evidence from every selected card, and `actions` must contain at least one `{text, reason, evidenceIds}` item whose evidence includes an anchor, application, or personal tier; the server derives bounded `actions[].evidence` entries with the validated `evidenceId`, `tier`, `sourceType`, `sourceLabel`, and `evidenceExcerpt` so clients can show action provenance without trusting provider metadata, `uncertainty` must be non-empty on the first reading, and top-level `references` are deduplicated by `evidenceId`, must cover every selected card, and must carry a non-empty `claim` that overlaps a concrete term in its evidence. When `coverageStatus` is `anchor_only`, or when `missingGoalCoverage` contains the routed goal, `uncertainty` must name the missing goal layer: advice must mention application/action/next-step evidence, forecast must mention prediction/trend/reference evidence, explanation must mention explanation/reason/clue evidence, and comparison must mention option/comparison/trade-off/condition/cost evidence; when forecast or comparison evidence is available, top-level `references` must include a matching reference-tier (forecast) or application-tier (comparison) citation; the server rejects a generic uncertainty sentence. `text`, `cardReadings.reading`, and `synthesis.text` also pass a calibration guard that rejects absolute predictive claims such as “保证一定会” or “绝对会”; explicit negated boundaries such as “牌面不能保证” remain valid. Any structured follow-up that includes `references` uses the same claim-support check and, when the active goal has matching evidence, must include a citation from that goal tier in `references` or the corresponding `goalSections`; structured follow-up `cardReadings` and `synthesis` also need meaningful overlap with their cited evidence, while a follow-up may omit references, actions, or synthesis and plain-text follow-ups remain readable for compatibility but still require a concrete overlap with the current evidence. When `needsClarification: true`, `clarification` must be one concrete question and `cardReadings`, `synthesis`, `actions`, and `references` must be empty so an open question cannot carry a partial fabricated reading. Clarification is allowed on a first turn only when both the theme and response goal are open; an explicit mixed goal plan must be answered in its validated sections, while an existing conversation may still ask one focused follow-up question. The optional `spread` object is checked against the fixed catalog (or a bounded custom layout) before it reaches the model. Each evidence item and derived reference also carries `sourceAuthority` (`canonical_fixed`, `historical_reference`, `contextual_reference`, or `user_context`); fixed card meaning is authoritative when external wording conflicts. Each reference includes an `evidenceId`, `cardId`, `position`, `claim`, a bounded `evidenceExcerpt` copied from the validated evidence, `kind`, `tier`, `source`, stable `sourceType` (`fixed_card_meaning`, `external_reference`, `personal_memory`, or `other`), `sourceLabel`, optional fixed `url`, and `retrievalReasons`; the client labels these provenance types separately and shows the excerpt so personal memory is visibly distinct from card meaning and each claim can be checked; references to personal memory must use `cardId:null` and `position:null`, while action evidence IDs may cite either selected-card evidence or relevant memory evidence. The model receives only the selected cards, the checked spread, and retrieved evidence, never the full 78-card corpus. Each context includes `knowledgeMeta` with the server-fixed deck version, RAG corpus version, and independent Prompt version; a client-supplied deck version is recorded for drift diagnosis but never allowed to change server meanings. The Prompt version is also returned by the interpret endpoint and debug response so evaluation can separate Prompt changes from corpus changes. A first reading must be structured JSON; high-stakes uncertainty must name a reality check such as materials, risk, or qualified professional review rather than a vague disclaimer; high-stakes decision verbs in action text must also carry a reality verification, risk assessment, or qualified professional advice cue; if the provider violates that contract, the server makes at most one repair request and rejects it if it is still plain text or malformed. Provider and middleware failures return stable `code` values such as `provider_auth`, `provider_balance`, `provider_busy`, `provider_timeout`, `provider_not_configured`, `rate_limited`, `card_reading_support`, `synthesis_support`, `missing_synthesis_anchor`, `clarification_payload`, `text_support`, `mixed_text_goal_coverage`, `followup_text_support`, `coverage_boundary`, `action_reason`, `action_reason_support`, `goal_section_support`, `goal_section_evidence`, `goal_section_tier`, `goal_section_route`, `missing_goal_sections`, `action_concreteness`, `missing_goal_reference_coverage`, `action_goal_evidence`, `goal_alignment`, `followup_question`, `missing_reality_boundary`, `professional_action_boundary`, `open_goal_prediction`, `timing_claim`, and `overconfident_claim`; the client maps them to recovery guidance without exposing upstream bodies. If the bounded repair still fails validation, the 502 response includes `{error, code}`; `code` is a stable parser code suitable for UI and telemetry.

When `activeQuestion` contains an explicit relationship, career, or reflection term, the same parser contract also requires top-level `text` to use at least one term from every explicit topic's vocabulary, so natural synonyms such as `考试` and `学习` remain compatible; open or choice-only questions skip this narrow relevance check. A mismatch returns the stable `question_relevance` code and receives a bounded repair prompt, so evidence-backed but off-topic generic prose cannot reach the client. The parser also checks the routed response mode: `advice` must contain an actionable next-step expression, `forecast` must contain both a trend cue and a reality-check cue in the answer or uncertainty boundary, `explanation` must state a cause or card clue, and `comparison` must name conditions, costs, or trade-offs; mixed readings apply the check to each `goalSections` entry. A mismatch returns the stable `goal_alignment` code and uses the same single bounded repair. If the model returns `followUp`, the server also requires one concrete question tied to the active question or goal; generic prompts and multiple questions return `followup_question` and use the same bounded repair.

## Deployment boundary
This integration runs on the LOCAL Vite dev/preview server. The preserved Sites worker still serves static assets only. Publishing the static build does not deploy this API; public hosting requires a separately authenticated backend and server-side secret configuration. Do not publish this local paid endpoint as an unauthenticated public proxy.
