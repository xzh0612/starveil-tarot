# Local DeepSeek reading backend

The local Vite dev and preview servers install `createReadingMiddleware` for:
- `POST /api/readings/interpret`: grounded Chinese reading and same-deck follow-ups.
- `POST /api/readings/debug`: local retrieval and Prompt diagnostics; it never calls DeepSeek and does not require an API key.
- `GET /api/readings/status`: configuration presence and model name, no credentials. This is not a provider health/balance check.

`POST /api/spreads/recommend` asks the model for 2–3 catalog spreads and validates each reason against the selected spread's position concepts and the question's recognized theme, rejecting generic or off-topic explanations before they reach the client.

Server-only settings in ignored `frontend/.env.local`:
```
DEEPSEEK_API_KEY=<local secret>
DEEPSEEK_MODEL=deepseek-flash
VITE_READING_ENDPOINT=/api/readings/interpret
```
Never prefix the API key with VITE_. The local file has mode 0600 and is not included in the client build. Change the key there and restart the local server after rotation.

The middleware permits loopback requests only and checks browser origin against the request host. It caps request size, validates card IDs/orientations/roles, retrieves a small grounded evidence set from `reading-rag.mjs`, asks for a JSON answer, and rejects references outside that set. The intent lexicon includes common expressions such as job changes, interviews, exam preparation, cold wars, renewed contact, anxiety, and fatigue, while weak pronouns remain fallback signals; this keeps ordinary Chinese phrasing from becoming an open route. Each evidence item carries a stable `tier` (`anchor`, `application`, `reference`, or `personal`), deterministic `retrievalReasons`, the exact `retrievalTerms`/`retrievalDirectTerms`/`retrievalExpandedTerms`/`retrievalThemes`/`retrievalPositionKinds`/`retrievalGoals` that contributed to selection, and bounded `retrievalMethod`/`retrievalScore`/`retrievalSemanticScore` metadata from the BM25-plus-rules ranker and optional semantic reranker, so the model can prioritize core card meaning and the server can audit why a chunk was selected; expanded terms are low-weight lexicon hints rather than user claims. Personal memory retrieval uses a stricter keyword threshold (`memory-keyword-v2`): a record needs one concrete phrase, one informative short term, or several independent short matches before it is sent to the model; returned memory evidence is marked `memoryStatus:user_confirmed` and `memoryUse:context_only`, and the memory text is fenced as untrusted data; generic words such as “怎么/安排/自己” alone do not expose a private record. `retrieveReadingEvidence` accepts an optional server-side `semanticScores` map and `semanticWeight`; the default map is empty and makes no embedding or network call. For an asynchronous model, `retrieveReadingEvidenceAsync` passes the untrimmed candidate set to a `semanticReranker({question,cards,evidence})` callback, waits at most 1.5 seconds by default, then applies the same budget and diversity rules; callback failures or timeouts fall back to lexical retrieval. `createReadingMiddleware` accepts the same callback and uses the resulting evidence both in the Prompt and in response citation validation. A future local model or authenticated backend can provide 0–1 scores without changing the Prompt contract. The ranker is deliberately dependency-free and keeps its scoring interface replaceable for a future vector reranker. Each selected card always retains symbolism and orientation anchors; `retrievalRequired` marks those chunks. The Prompt also receives `evidenceMeta`, a diagnostic summary of tier/kind counts, semantic coverage, selected cards, per-card anchor/application coverage, and goal-level support (`goalCoverage`/`missingGoalCoverage`) so a forecast or comparison without its matching evidence layer is visible to the model. A derived `evidencePlan` lists per-card anchor/application/reference IDs, `positionEvidenceIds` for evidence selected because it matches the card position, all goal evidence IDs, and `goalRequiredEvidenceIds` at the tier required by each routed goal, plus personal evidence IDs as a citation index; when `positionEvidenceIds` is present, the Prompt requires each first-reading card explanation to cite at least one position-specific chunk before generic application/reference evidence; the parser enforces the same rule during bounded repair; it carries no additional card meaning. Its `coverageStatus` is `complete` only when every card has both core anchors and the current theme application evidence; `anchor_only` or `incomplete` requires narrower uncertainty rather than invented meaning. A global evidence budget first rotates optional evidence across cards by score, then fills a second chunk for a card only after every represented card has had a chance; the default budget grows with card count and the number of application domains for large mixed spreads (capped at 96), while an explicit budget remains respected, so large spreads do not crowd the Prompt with low-priority references. For mixed questions, the retriever also reserves one required-tier chunk for each routed goal when the default budget allows it, then reserves one application chunk for each explicit relationship, career, or reflection domain before filling the remaining budget with references; a choice-only or domain-neutral advice/comparison question reserves the reflection chunk as a decision context, and a focused question still filters unrelated application chunks. Temporal context words such as “未来” and “接下来” receive a low forecast weight unless paired with an explicit prediction phrase; this keeps “未来我该怎么办” on the advice route while “未来会怎样” remains forecast. The intent router separately scores the requested goal (`advice`, `forecast`, `explanation`, or `comparison`) so the same topic can receive different evidence weighting and response emphasis. The prompt keeps the original question as the reading's background but derives `activeQuestion` from the latest real user message, so follow-up retrieval, memory matching, and intent routing follow what the user is asking now. A generic follow-up may inherit the original question in the server-generated retrieval query to preserve the spread context; the active question remains the latest user message sent to the model for direct response. For a focused single-theme question, only the matching application kind is retained; mixed questions keep multiple application kinds. High-stakes protection is cumulative: the server keeps the reality-based boundary when either the original question or the active follow-up is health, legal, investment, or similar high-stakes content, so a generic follow-up cannot remove it. The prompt also receives a transparent `retrievalMeta` routing hint (`themes`, weighted `themeScores`, goals, `goalScores`, matched terms, confidence); explicit topic terms take precedence and weak pronouns only provide a fallback route. A server-generated `responsePlan` supplies a text range that grows with the number of cards, carries the routed goal (`advice`, `forecast`, `explanation`, `comparison`, `mixed`, or `open`) and a matching emphasis sentence, and requires a first-reading `synthesis` field that links the selected cards. A derived `goalPlan` preserves the router order for mixed goals and binds each goal to its required evidence tier and evidence IDs, so the model answers advice, forecast, explanation, or comparison sections separately instead of blending unsupported conclusions; mixed first readings also return validated `goalSections`, one per routed goal, and the server rejects missing sections or evidence from another goal; the system Prompt follows a fixed workflow of current-question extraction, per-card evidence grounding, first-reading synthesis/action coverage, follow-up focus, and final citation/self-check; neither routing metadata nor the plan is treated as a source of card meaning. The fixed context is wrapped in `<starveil_context>`, compacted history is wrapped in `<starveil_history>`, and a server-generated `<starveil_turn>` reminder is appended after history to restate the current question and checked card positions; system instructions say that text inside either data fence is never executable instructions. History is compacted deterministically to the most recent 24 messages, at most 4,000 characters per message and 24,000 characters total, so old conversation cannot crowd out the current evidence. The model-facing `evidence` keeps only stable identity, card position, tier, source provenance, orientation, and bounded text; retrieval terms, scores, and reasons stay in the local `retrievalDiagnostics`/debug response so ranker metadata does not consume model context or masquerade as meaning. The context also carries a diagnostic `promptBudget` with input/selected/omitted/truncated history counts, history/evidence/memory character totals, question lengths, and evidence/memory item counts; it is observability metadata only and never a source of meaning. On the first reading, every selected card, a cross-card synthesis, a non-empty uncertainty section, and at least one evidence-backed action are required; each card reading must both cite a core anchor and overlap a meaningful concept from its cited evidence, the first synthesis must also overlap a meaningful concept from its cited evidence, while each first-reading action must include a time, count, scope, or outcome marker and cite anchor, application, or personal evidence. Malformed output gets at most one structure-repair request before the same validation runs again, and that repair prompt includes a stable validation code while fencing the prior output as data. Health, legal, investment, and similar high-stakes questions require a non-empty reality-based uncertainty boundary. It limits request concurrency/rate and has a 90-second timeout with disconnect cancellation. Only the current question/cards/conversation and explicitly enabled, question-relevant memory records go to DeepSeek; disabled, unrelated memories and archives are not transmitted. Past demo assistant answers are excluded from model context.

## Reading contract

`POST /api/readings/interpret` returns `{text, source, provider, model, promptVersion, needsClarification, clarification, goalPlan, goalSections, cardReadings, synthesis, actions, references, followUp, uncertainty, evidenceMeta}`. `goalPlan` preserves the routed goal order and binds each goal to its required evidence tier and evidence IDs, so a future client can show which part of a mixed answer is advice, forecast, explanation, or comparison. For a mixed first reading, `goalSections` contains one validated section per routed goal with its own evidence; the server rejects missing sections, unrequested goals, or evidence belonging to another goal. `cardReadings` includes the locked `orientation` (`正位` or `逆位`) so the client can show which fixed card meaning was used, plus server-derived `evidence` entries with bounded source labels and excerpts; `synthesis` and `actions` expose the same derived evidence shape so each visible explanation can be traced without trusting provider-supplied metadata. Personal-memory evidence additionally carries `memoryStatus:user_confirmed` and `memoryUse:context_only`; these are policy markers, not card meaning. `evidenceMeta.coverageStatus` reports whether the retrieved set fully covers each card's core and current-theme application evidence (`complete`, `anchor_only`, or `incomplete`); the client displays this diagnostic without treating it as a new card meaning. On the first structured reading, top-level `text` must overlap a meaningful concept in the evidence cited by the response, `cardReadings` must contain every selected card with matching `evidenceIds`, at least one core anchor per card, and prose that overlaps a meaningful concept in one of those evidence chunks, while `synthesis.text` must overlap a meaningful concept from the cited evidence for every selected card and `synthesis.evidenceIds` must include a core anchor for every selected card, each first-reading action must include a non-empty `reason` explaining its connection to the reading, with the reason sharing a meaningful concept with its cited evidence, plus a time, count, scope, or outcome marker; when an advice or comparison goal has available application evidence, every first-reading action must cite at least one application-tier evidence ID for that goal; `synthesis` must contain `{text, evidenceIds}` citing card evidence from every selected card, and `actions` must contain at least one `{text, reason, evidenceIds}` item whose evidence includes an anchor, application, or personal tier; the server derives bounded `actions[].evidence` entries with the validated `evidenceId`, `tier`, `sourceType`, `sourceLabel`, and `evidenceExcerpt` so clients can show action provenance without trusting provider metadata, `uncertainty` must be non-empty on the first reading, and top-level `references` are deduplicated by `evidenceId`, must cover every selected card, and must carry a non-empty `claim` that overlaps a concrete term in its evidence. When `coverageStatus` is `anchor_only`, or when `missingGoalCoverage` contains the routed goal, `uncertainty` must explicitly state that application, forecast, or comparison evidence is limited; when forecast or comparison evidence is available, top-level `references` must include a matching reference-tier (forecast) or application-tier (comparison) citation; the server rejects a generic uncertainty sentence. `text`, `cardReadings.reading`, and `synthesis.text` also pass a calibration guard that rejects absolute predictive claims such as “保证一定会” or “绝对会”; explicit negated boundaries such as “牌面不能保证” remain valid. Any structured follow-up that includes `references` uses the same claim-support check; structured follow-up `cardReadings` and `synthesis` also need meaningful overlap with their cited evidence, while a follow-up may omit references, actions, or synthesis and plain-text follow-ups remain readable for compatibility. When `needsClarification: true`, `clarification` must be one concrete question and `cardReadings`, `synthesis`, `actions`, and `references` must be empty so an open question cannot carry a partial fabricated reading. The optional `spread` object is checked against the fixed catalog (or a bounded custom layout) before it reaches the model. Each reference includes an `evidenceId`, `cardId`, `position`, `claim`, a bounded `evidenceExcerpt` copied from the validated evidence, `kind`, `tier`, `source`, stable `sourceType` (`fixed_card_meaning`, `external_reference`, `personal_memory`, or `other`), `sourceLabel`, optional fixed `url`, and `retrievalReasons`; the client labels these provenance types separately and shows the excerpt so personal memory is visibly distinct from card meaning and each claim can be checked; references to personal memory must use `cardId:null` and `position:null`, while action evidence IDs may cite either selected-card evidence or relevant memory evidence. The model receives only the selected cards, the checked spread, and retrieved evidence, never the full 78-card corpus. Each context includes `knowledgeMeta` with the server-fixed deck version, RAG corpus version, and independent Prompt version; a client-supplied deck version is recorded for drift diagnosis but never allowed to change server meanings. The Prompt version is also returned by the interpret endpoint and debug response so evaluation can separate Prompt changes from corpus changes. A first reading must be structured JSON; high-stakes uncertainty must name a reality check such as materials, risk, or qualified professional review rather than a vague disclaimer; if the provider violates that contract, the server makes at most one repair request and rejects it if it is still plain text or malformed. Provider and middleware failures return stable `code` values such as `provider_auth`, `provider_balance`, `provider_busy`, `provider_timeout`, `provider_not_configured`, `rate_limited`, `card_reading_support`, `synthesis_support`, `missing_synthesis_anchor`, `clarification_payload`, `text_support`, `followup_text_support`, `coverage_boundary`, `action_reason`, `action_reason_support`, `goal_section_support`, `goal_section_evidence`, `goal_section_tier`, `goal_section_route`, `missing_goal_sections`, `action_concreteness`, `missing_goal_reference_coverage`, `action_goal_evidence`, `missing_reality_boundary`, and `overconfident_claim`; the client maps them to recovery guidance without exposing upstream bodies. If the bounded repair still fails validation, the 502 response includes `{error, code}`; `code` is a stable parser code suitable for UI and telemetry.

## Deployment boundary
This integration runs on the LOCAL Vite dev/preview server. The preserved Sites worker still serves static assets only. Publishing the static build does not deploy this API; public hosting requires a separately authenticated backend and server-side secret configuration. Do not publish this local paid endpoint as an unauthenticated public proxy.
