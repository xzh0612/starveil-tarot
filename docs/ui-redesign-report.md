# Starveil Tarot UI 重设计报告

> 目标：把当前“带动效的场景海报”升级成可以被操作、拆分、编排的 3D 占卜空间。
>
> 这份报告只记录设计方案和实现边界，当前不修改业务代码，也不提交 GitHub。

## 1. 设计结论

当前项目已经有 React、Three.js、78 张固定牌、牌阵、DeepSeek 解读、档案和真实 GLB 女巫模型。问题主要集中在表现层：

- `PosterScene.jsx` 目前用两张场景图片配合 Shader 做局部流动，房间、桌子和人物并不是真正的空间对象。
- 女巫 GLB 在 `WitchStudio.jsx` 中可以单独预览，但没有成为占卜室里的主角。
- 牌带是 CSS 绝对定位的图片，虽然支持拖动，但没有真实的厚度、遮挡、桌面接触和光照。
- 进入、抽牌、翻牌、解读和档案之间缺少连续的镜头、灯光和角色动作编排。
- 面板打开后更像覆盖在背景上的窗口，而不是房间中的抽屉、书架或桌面物件。

下一版采用“可拆分舞台”的结构：

```text
场景容器
├── 房间建筑层：墙、窗、帷幔、书架、地面
├── 光照层：月光、烛光、桌面反射、局部体积光
├── 女巫角色层：头部、兜帽、法袍、双手、饰品、动作骨骼
├── 桌面层：桌板、布料、法阵、蜡烛、晶球、墨水
├── 牌组层：78 张独立卡片、牌背、卡面、阴影、选中状态
├── 粒子层：星尘、火星、烟雾、法阵微粒、鼠标吸引场
└── UI 叠加层：问题、牌阵、解读、档案和辅助操作
```

每一个对象都有自己的位置、材质、动画通道、交互事件和可见性。背景只负责提供空间，不再承担人物、桌子和所有动效。

## 2. 设计方向

### 2.1 视觉主题：紫黑星象书房

整体不是纯黑桌面，也不使用大面积廉价紫色发光。色彩采用深紫空间配暖烛光：

| 用途 | 色值 | 用法 |
| --- | --- | --- |
| 夜幕底色 | `#080712` | 房间阴影和 UI 背板 |
| 深紫木材 | `#1B1228` | 书架、桌体、门框 |
| 午夜紫 | `#2C173F` | 女巫法袍和帷幔 |
| 星象紫 | `#7150A8` | 法阵、选中、粒子高光 |
| 烛火金 | `#F2B56B` | 蜡烛、牌边、提示状态 |
| 羊皮纸 | `#E6D7D0` | 牌面文字和正文 |
| 雾银 | `#B5A7C6` | 次要说明和状态 |

紫色只负责空间气氛和状态提示，牌面仍保持 RWS 的米白、墨线和复古色，保证可读性。

### 2.2 材质语言

- 墙面和木柜：粗糙度较高的 PBR 材质，带微弱木纹法线。
- 桌面：深紫色天鹅绒或磨砂木，不使用全黑纯色；用真实粗糙度接住牌和手的阴影。
- 法袍：半哑光布料，边缘金线单独做材质，布料飘动由骨骼和轻量顶点偏移完成。
- 牌面：正面为固定 RWS 图片，背面为独立 3D 牌背材质；边缘有薄金属倒角。
- UI 面板：半透明羊皮纸和深色玻璃只用于小面积信息层，保留房间透视和烛光反射。
- 粒子：使用低亮度星尘和暖色火星，避免整屏霓虹噪声。

## 3. 技术方案

### 3.1 保留的技术

继续使用 React + Vite + Three.js，不立即迁移到另一套渲染框架。当前项目已经有 Three.js、GLB 加载、动作预览和移动端降级逻辑，保留这些基础可以降低风险。

推荐新增或整理为以下模块：

```text
src/scene3d/
├── TarotStage.js          场景根节点和生命周期
├── stage-assets.js        GLB、纹理、牌面资源清单
├── stage-cameras.js       每个页面的相机轨道和镜头目标
├── stage-lights.js        月光、烛光、牌面补光和状态灯
├── witch-rig.js           女巫骨骼、动作、IK 和镜头朝向
├── card-rig.js            单张牌的 3D 实例、翻面和飞行
├── fan-deck-3d.js         78 张牌的扇形布局、拖动惯性和射线命中
├── particle-systems.js    星尘、烟雾、火星、法阵粒子
├── stage-interaction.js   Raycaster、指针、拖动和键盘操作
└── stage-performance.js   设备等级、降级、可见性和帧率策略
```

业务层仍由 React 管理，例如当前页面、选中的牌和解读消息；Three.js 只负责舞台对象和动画。两层通过稳定的事件协议连接：

```text
React 状态                  3D 舞台动作
view='draw'          →      相机移动到牌桌 + 女巫 Offer 动作
selected=[...]       →      卡片沿飞行轨迹进入牌位
revealed=[...]       →      对应卡片翻转 + 烛光短暂增强
panel='archive'      →      相机推向书架 + 书本抽出
action='thinking'    →      女巫低头 + 桌面法阵呼吸
```

### 3.2 真实 3D 资产拆分

Blender 导出不再只给一张完整人物图，而是保留可控制的节点和材质：

```text
witch.glb
├── Witch_Root
├── Witch_Spine
├── Witch_Head
├── Witch_Hood
├── Witch_Cloak_Main
├── Witch_Cloak_Trim
├── Witch_Left_Arm
├── Witch_Right_Arm
├── Witch_Left_Hand
├── Witch_Right_Hand
├── Witch_Jewelry
└── Witch_Eye_Glow
```

桌面和房间也拆成独立节点：

```text
room.glb      墙、窗、帷幔、书架、月亮投影
table.glb     桌板、桌布、法阵、蜡烛、晶球
cards.glb     可复用牌背、牌框和牌槽
props.glb     书、墨水瓶、羽毛笔、沙漏和档案盒
```

这样可以实现“翻牌时只动牌和手”“打开档案时只动书架和镜头”“女巫说话时只动头部和眼部”，不会再把整张背景一起缩放或位移。

### 3.3 女巫动作系统

先制作可循环的基础动作，再为牌局事件拼接短动作。每个动作都可以单独触发，也可以与镜头和灯光同步。

| 状态 | 女巫动作 | 镜头和灯光 |
| --- | --- | --- |
| `entry` | 站在书房侧后方，抬手推开门帘 | 月光从门后进入，粒子向室内流 |
| `sanctum` | 坐在桌前轻微呼吸，手指触碰桌面 | 镜头慢速环绕，蜡烛亮度呼吸 |
| `listening` | 头部向用户一侧倾斜，兜帽略微转动 | 用户指针附近出现微弱紫光 |
| `thinking` | 低头看牌，右手沿法阵移动 | 法阵线条逐段点亮，烟雾上升 |
| `shuffle` | 双手洗牌，袖口和金线轻微摆动 | 桌面相机下降，牌背反光增强 |
| `offer` | 双手放回桌面，掌心靠近牌带 | 牌带中心形成可交互光环 |
| `drawing` | 一只手向被选牌伸出，另一只手保持支撑 | 被选牌获得暖色边缘光 |
| `reveal` | 眼睛短暂抬起，手指轻触牌边 | 卡面翻开瞬间，烛光闪一下 |
| `speaking` | 上半身保持稳定，头部和手势做小幅变化 | 解读文字逐句出现，粒子向文字汇聚 |
| `archive` | 女巫退到画面边缘，保持侧身守夜 | 镜头推向书架，前景书本产生景深 |

面部可以先保持遮挡和紫色眼睛的识别特征，后续再加眼睛、口型和面部表情。第一版必须确保动作即使没有面部动画也成立。

## 4. 页面和互动设计

### 4.1 入口：推开星幕

入口不再是整张门的平面图片。前景是两扇可独立旋转的木门，门后是 3D 书房，女巫只在远处的半透明帷幔后出现。

互动：

- 鼠标移动时，门缝内的星尘朝指针方向聚集。
- 鼠标靠近门把手，门把手出现暖色反光，门缝增大一点。
- 点击后，两扇门沿真实铰链打开，镜头穿过门缝进入书房。
- 如果用户不操作，蜡烛和星尘仍然有低频运动，但不会自动播放夸张剧情。

### 4.2 占卜室：问题先落到桌面

用户进入房间后，页面中心是桌面和女巫上半身。问题输入不是底部固定条，而是一张可以放在桌面上的羊皮纸卡片。

互动：

- 点击羊皮纸后，镜头轻微推近，羽毛笔和墨水瓶亮起。
- 输入文字时，纸面上的细小星点按文字节奏亮起。
- 提交后，羊皮纸沿桌面滑到女巫面前，触发 `listening`。
- 牌阵推荐以桌面的三张浮动牌阵签展示，悬停时牌阵模型翻转，显示位置说明。

### 4.3 牌阵选择：桌面上的三维签牌

推荐牌阵不做普通卡片列表。每个牌阵是一个有厚度的牌阵签牌，放在桌面上形成扇形。

- 当前推荐的牌阵有暖色边缘光。
- 拖动桌面可以改变签牌的顺序。
- 点击签牌后，相机向桌面下降，牌阵位置在法阵上预演。
- 选择确认时，牌阵签牌收拢到左侧，右侧出现“开始洗牌”动作按钮。

### 4.4 抽牌：78 张独立牌的真实扇形

牌带使用 78 个独立的 3D 卡片实例，而不是一张图片或 CSS 卡片集合。

- 每张牌沿一条可调整的贝塞尔弧线分布，有真实旋转角度和厚度。
- 鼠标拖动牌带时使用惯性和阻尼，松开后自然滑行。
- 射线命中牌后，该牌抬高、向用户倾斜，牌边出现细窄金光。
- 选中牌沿弧线离开牌带，经过一条可见的粒子轨迹，落到指定牌位。
- 已选牌的位置留下空隙，让用户明确“这张牌已经被取走”。
- 牌位有真实的桌面阴影和轻微布料接触，不使用整块黑色背景。

### 4.5 翻牌与解读：桌面不是弹窗

翻牌时镜头停留在桌面高度，女巫只显示上半身和双手。牌面翻转使用绕 Y 轴的真实旋转，正面和背面分别有材质。

- 翻牌瞬间，桌面法阵只点亮与该牌位有关的环节。
- 卡面下方出现一条窄的牌位标签，不遮挡牌面。
- 右侧解读区域是一块悬浮羊皮纸，随当前牌位展开；它不会覆盖女巫和牌桌。
- 用户可以点击“逐牌”“综合”“下一步”切换讲述层级，每次切换由镜头焦点和粒子流向提示。
- AI 对话输入位于羊皮纸底部，回复时女巫头部和手势同步变化。

### 4.6 档案库：进入房间里的书架

档案不是一个大尺寸遮罩面板。镜头沿书架移动，历史占卜作为有厚度的书本排列。

- 鼠标靠近某本书时，书脊向外弹出，显示日期和问题摘要。
- 点击后书本被抽出，翻开到桌面；页面右侧显示该次牌阵和解读。
- 搜索结果通过书脊颜色和金色标签标出，不刷新页面。
- 删除、导出和备注操作放在书页边缘的小型工具条中。

### 4.7 牌义图鉴：抽屉式卡匣

78 张牌不再是固定的六列图片网格，而是三层结构：

1. 左侧是大阿卡娜和四个小阿卡娜抽屉。
2. 中间是当前抽屉中的 3D 卡匣，可以拖动浏览。
3. 右侧是选中卡片的立体放大、正逆位切换和来源说明。

卡片悬停会向前移动并接住烛光，点击后才翻开。这样图鉴同时展示“牌的物件感”和详细文字。

### 4.8 我的知识库：记忆盒

用户知识库用桌面上的抽屉盒表现。每条记忆是一个可编辑的纸条，启用状态用小蜡封表示。

- 打开抽屉时，只有抽屉、纸条和镜头动作，不重新加载场景。
- 新增记忆时纸条从羽毛笔下生成。
- 记忆默认关闭，用户主动打开后才可能进入 RAG；UI 中明确显示“仅作为上下文”。

## 5. 粒子系统设计

粒子不是一个整屏的紫色噪点层，而是四个用途明确的系统。

### 5.1 星尘 `StarDustSystem`

- 4,000 至 8,000 个 `InstancedBufferGeometry` 粒子。
- 初始位置使用固定 seed，避免每次刷新布局跳变。
- 低速垂直漂移，加一层缓慢噪声。
- 指针形成局部吸引场，距离越近偏移越明显。
- 移动端自动降到 1,200 至 2,000 个。

### 5.2 烛火 `CandleSystem`

- 火焰使用少量 billboard 粒子和 additive blending。
- 点光源强度由同一时间曲线驱动，火焰和桌面反光保持同步。
- 点击翻牌时只增强当前牌位附近的烛火，不让整屏闪白。

### 5.3 烟雾 `SmokeSystem`

- 使用 8 至 16 个半透明噪声 billboard，沿固定路径上升。
- 对象池复用，不在每帧创建和销毁对象。
- 烟雾只出现在香炉和蜡烛附近，避免遮挡牌面文字。

### 5.4 法阵 `RuneSystem`

- 用 `THREE.Line2` 或自定义线段材质绘制桌面圆环和符号。
- 根据当前牌位逐段点亮。
- 进入 `thinking` 时有 1.2 秒的呼吸周期；无操作时回到低亮度。

## 6. 交互技术细节

### 6.1 命中和拖动

- 使用 `THREE.Raycaster` 命中牌、书脊、门把手和抽屉。
- 触摸设备使用 pointer events，保持同一套事件协议。
- 拖动不修改 DOM 的 `top`、`left`，只更新 3D 对象的 transform 和 shader uniform。
- 牌带移动使用速度、阻尼和边界回弹三个参数。
- 所有可操作对象提供键盘焦点和文字提示，保证不依赖鼠标。

### 6.2 动画编排

每个页面只暴露一个场景状态和一个动作时间线。动画时间线不直接散落在组件里：

```js
const timelines = {
  draw: [
    ['camera.dolly', 0, 900],
    ['witch.offer', 160, 1100],
    ['deck.enable', 480, 0],
  ],
  reveal: [
    ['card.flip', 0, 720],
    ['runes.highlight', 120, 900],
    ['witch.reveal', 180, 820],
  ],
};
```

时间线只描述事件，不保存业务数据。业务状态仍由 React 管理，保证刷新、回放和存档不会被动画状态污染。

### 6.3 相机系统

使用三个基础相机目标：

```text
visitor   看女巫和房间
table     看牌桌、手和牌位
archive   看书架和档案书
```

每次切换使用带阻尼的相机轨道，不瞬移。用户拖动场景时允许小范围自定义视角，但不允许离开设计好的舞台边界。

## 7. 性能和降级

高级视觉必须可以在真实设备上运行，性能预算如下：

| 设备 | 粒子数 | 阴影 | 后处理 | 模型 |
| --- | ---: | --- | --- | --- |
| 桌面高性能 | 8,000 | 2048 软阴影 | Bloom + TAA | 高精度 GLB |
| 普通笔记本 | 4,000 | 1024 阴影 | Bloom | 压缩 GLB |
| 手机 | 1,500 | 512 阴影 | 无 Bloom 或极弱 | 低面数 GLB |
| `prefers-reduced-motion` | 0-500 | 简化 | 关闭 | 保留交互 |

实现要求：

- 不给整张大背景图做持续位移。
- 不在滚动容器上使用大面积 `backdrop-filter`。
- 粒子使用实例化和对象池。
- GLB 使用 Draco 或 Meshopt 压缩，并按页面懒加载。
- 页面隐藏时暂停渲染循环。
- 所有动画只改 `transform`、材质 uniform、骨骼或透明度。
- 如果 WebGL 不可用，保留当前 CSS/图片降级模式，业务流程继续可用。

## 8. 视觉验收标准

第一版不以“截图好看”作为完成标准，而以可观察的交互为标准：

1. 鼠标移动时，至少有三种独立对象响应：粒子、烛光、女巫或牌。
2. 抽牌时能看到单张牌从扇形中离开、飞行、落位和阴影接触。
3. 翻牌时女巫的手、牌面和法阵有时间上的对应关系。
4. 切换档案、图鉴和知识库时，空间中的物件发生动作，不能只出现 HTML 遮罩。
5. 用户关闭动效后，布局和主要功能仍然成立。
6. 手机端仍然是单屏体验，不要求上下滚动才能完成一次抽牌。
7. 所有牌面图案继续使用固定 78 张 RWS 资源，不由模型随机生成。
8. RAG、Prompt、DeepSeek 接口和现有数据存储不改变。

## 9. 实施顺序

建议分四个阶段，每阶段都能单独验收：

### 阶段 A：舞台基础

- 把房间、桌面、灯光和相机抽成独立 Three.js 节点。
- 保留当前页面状态和降级模式。
- 先让鼠标可以影响星尘、烛光和相机视差。

### 阶段 B：女巫和牌桌

- 将现有 `witch-v2.glb` 放入真实牌桌空间。
- 绑定 `idle`、`listening`、`thinking`、`offer`、`drawing`、`reveal`、`speaking`。
- 让双手和牌桌有接触阴影，修正现在的“人物立在背景上”的感觉。

### 阶段 C：78 张 3D 牌带

- 把 `FanDeck` 从 CSS 牌带替换成 3D 实例牌带。
- 完成射线命中、惯性拖动、选中、飞行、落位和翻牌。
- 把牌面资源接到现有固定牌组，不改变牌义和抽牌数据。

### 阶段 D：空间化 UI

- 将牌阵推荐、解读、档案、图鉴和知识库做成桌面物件、书架和抽屉。

## 18. Agent 全链路审视：这次实际修正了什么

这次审视的对象不只是 RAG。一个可控的 Agent 至少包含五层：

```text
用户问题/历史/个人记录（数据）
        ↓
问题路由 + 检索 + 证据预算（RAG）
        ↓
结构化 Prompt 与输出契约（Prompt）
        ↓
模型生成（Provider）
        ↓
服务端解析、证据绑定、现实边界校验（Validator）
        ↓
界面展示、反馈和下一轮状态（UI / Memory）
```

原来的设计已经有固定牌义锚点、证据等级、Prompt 限长和输出校验，这些是正确的基础；但它把“用户允许某条记忆长期参与未来解读”和“本局解读允许读取个人知识库”混成了一件事。这是 Agent 设计中的权限边界问题，不是单纯的 UI 问题。

### 18.1 个人知识库的旧问题、改法和收益

旧流程在 `frontend/src/App.jsx` 的 `read()` 中直接把所有 `enabled` 记忆发送给后端。`enabled` 只表示用户曾经允许这条记录作为候选资料，并不等于用户正在允许本轮读取。于是用户打开一个旧牌局继续追问时，模型可能获得用户没有预期带入本轮的个人信息；而且单靠前端过滤不能构成安全边界。

现在的流程分成两道门：

1. `frontend/src/domain.js:50` 的 `createSession()` 把 `usePersonalMemory` 初始化为 `false`。新牌局默认不读个人知识库。
2. `frontend/src/App.jsx:105` 只有当前牌局明确开启时，才发送 `usePersonalMemory:true` 和已长期允许的记忆候选。
3. `frontend/src/services.js` 将这个字段真正传到后端。之前只在调用方传入但服务适配器没有转发，这是一个容易被忽略的接口契约漏洞。
4. `frontend/server/readings.mjs:270-277` 服务端再次校验布尔类型，并在 `usePersonalMemory !== true` 时完全不执行个人记忆检索。这是防御性编程：即使有人绕过界面直接调用接口，也不能因为提交了 `memories` 字段就自动启用。
5. `memoryMeta` 明确记录 `enabled`、候选数量、实际召回数量和检索版本，UI 可以显示“本局已启用/未启用”，调试接口也能验证事实，而不是猜测模型看到了什么。

旧代码“不够好”的核心原因是把长期同意、候选资格和本轮使用混为一个布尔值；改后把它们拆成了会话权限和记录权限。好处是隐私边界更清楚、请求可审计、追问可以保持本局决定、服务端不会信任前端过滤结果。对应测试包括：新会话默认关闭、关闭时个人证据为 0、开启时只召回相关且已允许记录、debug 接口报告真实状态。

### 18.2 RAG 当前痛点与本轮修正

当前知识库只有 78 张固定牌及其编辑牌义、Waite 资料和补充参考，规模很小。因此直接引入向量数据库并不能自动提高质量，反而会增加嵌入版本、索引同步、延迟、费用和调试难度。当前最合适的路线仍然是“规则路由 + 本地词法召回 + 证据层级 + 可选 reranker”，而不是盲目堆技术。

本轮发现一个具体问题：中文疑问词“如何、怎么、怎样、是否”等能够参与词法打分，但它们通常只表达意图，不表达主题。比如“未来会怎样发展？同时我该怎么安排下一步？”中，“怎样”可能把反思段落的分数抬高，形成看似命中、实际不说明主题的证据。

现在 `frontend/server/reading-rag.mjs` 增加了 `GENERIC_QUERY_TERMS`，只从直接主题词中排除这些泛化疑问词，同时保留主题路由和目标扩展词。也就是说：“怎么处理这段关系”仍然会路由到关系主题和建议目标；“怎么”本身不会再被当作牌义证据；`retrievalDirectTerms` 能更诚实地表示真正命中的词。固定的 `symbolism`、`orientation` 锚点和应用层证据规则不受破坏。

这不是“删词越多越好”。如果把所有短词都删掉，会伤害中文召回；所以只过滤经过测试确认的意图词，并把它限制在查询侧，不改写知识库正文。

### 18.3 市面检索技术的客观取舍

| 技术 | 解决的问题 | 本项目决策 |
| --- | --- | --- |
| 倒排/BM25 | 精确词、低延迟、可解释 | 保留，作为基线 |
| 元数据过滤 | 牌位、正逆位、目标和主题约束 | 保留并继续加强 |
| Dense Embedding + ANN | 同义表达和语义召回 | 作为可选第二路，不默认开启 |
| Hybrid + RRF | 合并词法和语义排名，避免分数不可比 | 未来接入时优先 RRF，不直接线性相加 |
| Cross-encoder | 对少量候选做高精度重排 | 可在候选 10—30 条上使用，需测延迟 |
| ColBERT / late interaction | 长文细粒度匹配 | 当前语料太小，收益不足 |
| SPLADE | 稀疏语义扩展 | 与现有小语料词法扩展重复，暂缓 |
| HyDE | 先生成假设答案再搜索 | 可能放大塔罗预测偏差，暂缓 |
| GraphRAG | 实体关系和全局总结 | 当前没有稳定实体图，暂缓 |
| HNSW / IVF | 大规模向量索引 | 78 张牌不需要，暂缓 |

这里的“最高效”不是单项 benchmark 最高，而是综合准确性、可解释性、隐私、延迟、成本和可回滚性。Elastic 对混合检索推荐词法与向量结合，Qdrant 的混合查询文档也强调用 RRF 合并不同检索分数；Qdrant 的 reranking 说明了先便宜召回、再对小候选集做昂贵重排的两阶段结构。相关资料：[Elastic hybrid search](https://www.elastic.co/guide/en/elasticsearch/reference/current/semantic-text-hybrid-search.html)、[Qdrant hybrid queries](https://qdrant.tech/documentation/concepts/hybrid-queries/)、[Qdrant reranking](https://qdrant.tech/articles/hybrid-search-2/)。

所以本项目的升级顺序是：先把评测集和词法基线做可靠；再增加可关闭的 dense 召回；用 RRF 合并；最后才考虑 reranker。每一步必须在同一份 holdout 问题集上比较 `Recall@k`、目标层级覆盖率、无关证据率、延迟和 Prompt 字符数，不能因为某个单例问题改善就宣布 RAG 已经完成。

### 18.4 Prompt、工具和 Agent 边界

当前 Prompt 的正确分工是：RAG 负责“选什么证据”，Prompt 负责“怎样使用证据和遵守边界”，模型负责“组织自然语言”，解析器负责“拒绝无依据输出”。历史消息、问题、个人记忆和模型返回都被当作不可信数据包围，不应被当作新的系统指令。

当前项目没有让模型自由调用文件、网络或支付接口；这反而是合理的。工具一旦加入，应先定义名称、参数 schema、权限、超时、重试次数、幂等性、审计字段和失败回退，再接入 Agent。不能只给模型一个“万能工具”，否则检索、写入个人知识库和外部副作用会混在一起，难以追责。个人知识库写入也应和读取分开，并要求用户显式确认。

### 18.5 可复现验证

本轮新增并通过了以下检查：

```bash
node --test frontend/tests/domain.test.mjs frontend/tests/readings.test.mjs frontend/tests/services.test.mjs
node --test frontend/tests/reading-rag.test.mjs
```

结果分别为 108 项和 158 项通过；另外泛化疑问词的回归测试证明“怎样/怎么”不再作为直接主题证据。全量回归和生产构建仍是本轮结束前的必检项；在没有 holdout 评测和真实接口验证之前，不把“测试通过”表述成“Agent 已经不需要改进”。

## 19. 第二轮 RAG 改进：BM25 不再只看单张牌

### 19.1 旧实现为什么不够准确

旧版 `collectReadingEvidence()` 调用 `scoreChunk()` 时，把当前牌的 7 个 chunk 作为 BM25 corpus。这样做的优点是简单，但 IDF 的参照范围太窄：一个词只要在当前牌的某个段落出现，就会被拿来和同牌其他段落比较；它不知道这个词是否在整局其他牌、其他资料中也很常见。结果是“局部命中”容易被误认为“全局区分度高”。

这不等于原来的 RAG 完全错误。锚点、牌位规则和主题过滤仍然提供了重要约束；问题主要出在词法分数的统计范围和诊断名称不够准确。

### 19.2 改后的实现

现在 `frontend/server/reading-rag.mjs` 在一次检索开始时，先把本局所有合法牌的候选 chunk 合成 `globalCorpus`，再把这个 corpus 传入每张牌的 BM25 评分。召回方法版本从 `bm25+rules+expansion-v1` 更新为 `bm25+rules+expansion-v2`，并新增回归测试确认一个多牌局使用整局候选语料计算词法相关性。

这样改的收益是：

- IDF 的参照范围和本轮候选集合一致；
- 同一个常见词不会只因为出现在某张牌的局部段落就获得虚高分；
- 诊断信息明确告诉我们当前使用的是哪一版排序算法；
- 仍然保留 `retrievalRequired` 锚点、牌位命中和全局证据预算，因此不会为了 BM25 分数牺牲牌面覆盖。

当前仍然没有把 78 张牌的所有内容永久建成向量索引，因为项目语料小且需要可解释、可回滚。下一步会用人工标注问题集验证全局 corpus 是否真的降低无关证据率，而不是只凭代码结构推断质量提升。
